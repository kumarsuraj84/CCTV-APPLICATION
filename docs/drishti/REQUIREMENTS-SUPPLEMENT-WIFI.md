## Module 9: Network and Wi-Fi management

Environment: ~10 NETGEAR Wi-Fi APs at head office, ~4–5 per store; each store has its own network/IP pool; SD-WAN with management addresses reachable from HO; multiple NETGEAR models (WAX615 mentioned — verify all actual models and firmware versions). Do not assume a device described as a router operates as a router; record its actual role.

Primary objective: make an intended configuration change once in Drishti and deploy it to an explicitly selected scope of compatible APs, with verification and clear per-device results. Do NOT automatically mirror a manual change on one AP to the others; detect it as drift, show the difference, and let an authorised user promote an approved change into a managed profile.

### A. Inventory and network pools
Extend the shared location and asset inventory (no disconnected duplicate records). Record: location/hierarchy; role (AP, router, switch, other); manufacturer, exact model, firmware; serial, hardware MAC, stable asset identity; management IP/hostname and VLAN; management mode (standalone, Insight-managed, other); supported monitoring and configuration methods; credential reference; reachability, last observation, capability-discovery time; configuration ownership and assigned profile.
Per-location network definitions: management subnet/CIDR; gateway/DNS; management VLAN; staff/guest/device VLAN mappings; approved discovery ranges; SD-WAN routing/NAT context. Validate addresses against the correct location, flag conflicts/unexpected placement; never copy HO addresses/gateways/VLANs into store configs; IP is never the sole identity. CSV import with validation, preview and actionable row errors.

### B. Capability discovery before automation
Inspect official documentation for exact model/firmware/mode. Capability matrix: inventory retrieval; health and client metrics; configuration read; SSID/security; MAC access lists; radio settings; backup/restore; firmware upgrade; reboot; supported API/controller/SNMP/SSH methods. Prefer documented vendor interfaces. Evaluate NETGEAR Insight only if the account, licensing and officially supported access permit it — do not assume a public API or invent endpoints. SNMPv3 for supported telemetry; verify vendor MIB coverage before promising configuration changes. Do not treat all NETGEAR devices as having the same API/CLI. Unsupported operations stay visible as unsupported with a precise explanation. Never change management mode automatically; document configuration-reset/reboot implications before any future mode migration. Web-UI-only operations: isolate as experimental model-specific adapters requiring lab validation; no silent brittle browser automation as a fleet-ready dependency.

### C. Configuration profiles
Versioned Wi-Fi profiles: global baseline; location overrides; explicit per-device overrides where justified; preview of each device's resolved configuration. Settings where verified: SSID create/rename/enable/disable; security mode and passphrase rotation; guest isolation and supported restrictions; SSID-to-VLAN mapping; MAC allow/deny lists with explicit mode and attachment scope; radio band/channel/width/transmit power; schedules; NTP/syslog; other documented model capabilities. Unique device/location settings stay separate from shared policy. A common profile must never cause duplicate management IPs. Do not assign the same radio channel to every AP merely because they share an SSID profile — preserve automatic radio management or a deliberate site plan. MAC filtering is an administrative restriction, not a replacement for authentication; account for client MAC randomisation in diagnostics. Passphrases/admin credentials stored securely; never displayed in diffs, exports or logs by default.

### D. Rollout workflow
Draft → validate → resolve targets → preview diff and impact → approve when required → schedule → canary → bounded rollout → verify → completed/partial failure. Scopes: selected APs; all APs at a location; selected locations; compatible model groups; organisation-wide with explicit targeting.
Before execution: verify permissions, capabilities, current state, firmware compatibility; capture an encrypted configuration snapshot where supported; show unsupported devices and excluded settings; detect conflicting jobs or stale configuration versions; estimate disruption/reboot/reconnection.
During: bound concurrency globally and per location; normally one AP at a time per location; preserve remaining coverage; use the wired/SD-WAN management path; maintenance windows, canaries, pause, failure thresholds; reconcile interrupted jobs before retrying; revalidate offline-device jobs on return; supersede outdated config jobs.
After: re-read settings and compare with desired state; distinguish accepted vs verified; AP reachability vs actual wireless-client connectivity; show requested, applied, verified, failed, unknown separately. No assumed atomic transaction across APs; partial application visible and recoverable.

### E. Scenarios to implement and demonstrate
1 staff SSID password across all APs in one store; 2 same approved SSID policy to selected stores keeping local network mappings; 3 add/remove a MAC rule on all selected compatible APs; 4 guest SSID with supported isolation; 5 detect an AP differing from its assigned profile; 6 exclude incompatible models before deployment; 7 unreachable AP returning after the intended password/profile has changed again; 8 recover from a partially completed deployment; 9 prevent a store-scoped operator changing another store's APs; 10 prevent two concurrent jobs overwriting each other. Password rotation can disconnect printers/scanners: include impact acknowledgement and verification steps; do not claim unsupported dual-password transition.

### F. Monitoring and proactive alerts
AP online/offline/stale; uptime and unexpected reboot; connected clients; radio state/utilisation; traffic and errors; firmware and configuration compliance; PoE/uplink health via AP/switch telemetry; weak client signal, retries, congestion when exposed; unexpected unassigned APs in approved discovery ranges; pending/failed configuration changes. Keep parent-dependency correlation: a store WAN outage is one location incident, not a notification storm per AP. Do not infer AP failure merely because HO cannot reach it.

### G. UX
Fleet overview with filters and actionable counts; location view; AP detail (capabilities, telemetry, configuration, history); profile editor with version history; effective-configuration preview; rollout planner with per-target differences; deployment progress and exception handling; drift/compliance view. Compact operational screens; detail in contextual help and investigation panels; shared Drishti design.

### H. Permissions and audit
Separate: view inventory/health; view redacted configuration; edit profiles; approve deployments; execute deployments; reboot/upgrade; restore configuration; retrieve/manage credentials. Location scope on server-side reads and writes. Audit actor, targets, profile version, redacted diff, approval, schedule, per-device result. Approval pinned to an immutable payload; post-approval changes need revalidation/renewed approval.

### I. Local validation
No scanning/login/reboot/reconfiguration/upgrade of real APs without explicit hardware authorisation. Local fake adapters and realistic model/firmware fixtures. Test: separate network pools; mixed capabilities; permission boundaries; profile inheritance and location overrides; secret redaction; drift detection; partial failure and unreachable devices; job expiry/supersession; lost acknowledgements and duplicate delivery; concurrent deployment conflicts; firmware/config compatibility; recovery and rollback limits. Produce a first-hardware-pilot checklist naming exact model, firmware, credentials/access method and low-impact scenarios. A mocked adapter proves orchestration only — never claim it proves real NETGEAR configuration support.
