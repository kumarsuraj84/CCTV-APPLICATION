# CityKart Drishti (CKDRISHTI) — delivery status: requirements to evidence

The single requirements-to-evidence tracker for the whole application, including the Wi-Fi module, as required by `docs/drishti/REQUIREMENTS-SUPPLEMENT-WIFI.md` ("Handover additions"). One row per requirement, one table per area. Every row carries the status that is true today. Baseline written 2026-10-22 on branch `feat/plan-3-live-feeds` at commit `3fc5c1f` (`feat: fast playback through ffmpeg`).

Sources of the rows: `docs/drishti/REQUIREMENTS-DIRECTIVE.md`, `docs/drishti/REQUIREMENTS-SUPPLEMENT-WIFI.md`, `docs/drishti/DECISIONS.md`, requirement IDs and current-state findings from `docs/audit/INITIAL-AUDIT.md` section 6, and the phase/work-package mapping from `docs/audit/REWORK-PLAN-PROPOSAL.md` sections 9.4 and 9.8. Rows whose ID starts with `WF-` come from the Wi-Fi supplement (it has no IDs of its own). Rows marked "tracker-added" are not in the proposal's traceability table (see "Gaps in the inputs" at the end of the Update rules).

## Status vocabulary (exactly five; the owner's wording)

| Status | Meaning in this tracker |
|---|---|
| `Implemented and locally verified` | Code exists and automated tests (or a recorded local check) pass on the current branch. Nothing in the row depends on real hardware or an outside system. |
| `Implemented but awaiting hardware validation` | Code exists and passes tests against local fakes, fixtures or synthetic data only (for example NVR ISAPI paths against the fake NVR). Behaviour on the real device is unproven. A fake proves orchestration, not vendor behaviour. |
| `Partially implemented` | Part of the requirement exists and works locally; a named part is missing, or a built part still follows the pre-directive design. The cell says which part. |
| `Blocked by a specific external dependency` | The requirement cannot be completed without a named outside input (data, access, licence, hardware, decision by a third party). The dependency is named in the last column. Work that does not need the input still proceeds and is described in the same cell. |
| `Not implemented` | No working code for the requirement, or the code does the opposite of the directive (such rows say so). Design-only material in `docs/superpowers/plans/` does not count as implementation. |

## How evidence is recorded

- The "Validation evidence" column names what proves the status today: `Test:` (file under `tests/`, with the exact test title where one test carries the claim), `Ledger:` (result reported by the builder ledger `.superpowers/sdd/2026-10-22-plan-3-live-feeds/progress.md`), `Audit:` (a section of `docs/audit/INITIAL-AUDIT.md`), `Code:` (read in the audit, no test), `Screenshot:` (a file under `docs/drishti/evidence/` or the existing `docs/design/reference-screenshots/`), `Doc:` (a document that exists).
- "none" means no evidence exists yet. A row with status `Not implemented` normally has only `Audit:` evidence of absence.
- **Baseline caveat.** The baseline statuses come from the audit and the builder ledgers. The test suites were not re-run when this file was written (documentation-only task; builders are active in the tree). Ledger figure at commit `2b5dc2f`: 774 unit and 290 integration tests passing. Rows marked `Implemented and locally verified` therefore rest on ledger results until the first fresh run is entered in the Evidence log; if that run fails, the row drops.
- The date-stamped, append-only record of results (commit, test command and result, screenshot path) is the "Evidence log" at the end of this file. A table cell may summarise; the Evidence log is authoritative.
- Quick counts at any time (run in PowerShell or Git Bash from the repository root): `grep -cE "^\| [A-Z]+-[A-Z]*[0-9]+ \|.*\| Not implemented \|" docs/drishti/DELIVERY-STATUS.md`, and the same with each of the other four status strings (the anchor stops this paragraph counting itself). Per-area counts: count the status string between the area's heading and the next heading.

## Update rules

1. Every work package updates its rows in this file in the same commit that merges the package locally. A package is not complete until its rows and the Evidence log are updated.
2. A status moves up only with evidence recorded in the Evidence log (commit, test command with result, or screenshot). Moving a row down (for example when a fresh run fails, or when a later change breaks it) needs no approval and is done immediately, with an Evidence log row saying why.
3. `Implemented and locally verified` needs automated tests (or a recorded local check) passing on the current branch, plus the typecheck, lint and build gates for the package (VA-1). It must not be used if any part of the row depends on a real device, a real network or an outside system.
4. Never claim real-hardware validation from fakes. Anything exercised only against the fake NVR, fake ffmpeg, fake adapters, synthetic data or the demo stream is at most `Implemented but awaiting hardware validation`. A Wi-Fi row stays there until the owner has authorised hardware and a pilot run against the named model and firmware is recorded.
5. `Blocked by a specific external dependency` must name the dependency (proposal 9.7 number or a plain description) in the last column, and the row returns to a normal status when the input arrives. Do not use it for work that is simply not yet scheduled.
6. Screenshots go in `docs/drishti/evidence/`, named `<row-id>-<what>-<viewport>.png` (for example `BR-3-login-logo-1366.png`), and are referenced from the Evidence log. Screenshots of the Asset Management reference stay in `docs/design/reference-screenshots/`.
7. Add a row when a requirement appears that has none. Mark the ID "tracker-added" in the requirement text, as with AR-9, and record the reason. Do not renumber existing IDs.
8. Do not copy secrets, tokens, passwords, passphrases or real device addresses into this file or into the Evidence log.
9. Quote test names exactly as they appear in the test file; do not cite a test that does not exist. If a cited file or test is renamed, update the row.
