# CityKart Drishti — Release 1 (first production release): camera feeds, grouping and access

Owner decision (2026-10-22): production go-live happens when **camera feeds and their grouping are complete**. In production the owner will add users and NVRs, build groups region-wise, cluster-wise, location-wise, organization-wise and camera-wise, and give users rights so each person sees only their allowed cameras with their own login. Everything else is built later in logical order. The release branch goes to `main` only when the owner says so at that point (nothing is pushed or merged now; the push is an explicit owner instruction at release time).

## Scope of Release 1 (must be complete, tested and reviewed)
1. **Hierarchy and inventory:** Organization → Region → Cluster → Location → NVR (recorder) → Camera; locations with 2–3+ NVRs; regions/clusters/locations/NVRs/cameras admin screens; bulk "find cameras for all locations"; CSV import with validation and row errors (real estate: ~200+ locations, ~4,600 cameras); archive instead of delete; wording "Location".
2. **Access and users:** capability model (live / playback / export) with scopes organization, region, cluster, location, recorder, camera; explicit overlap rules; effective-access preview; expiry; revoke with reason; access review of migrated grants; operator role rename; super administrator; export only for IT administrators (E-1); ≤ 60 s revocation of open video sessions (P2-4); admin and sensitive-action protection (multi-factor for administrators, fresh sign-in for access changes).
3. **Camera feeds:** live walls (sub-stream grids, on-demand main stream) by region, cluster, location, NVR, saved group and single camera; camera groups: static lists and dynamic rules (region / cluster / location / NVR / name), never expanding access; playback by day with calendar and timeline (1x via the stream path; fast playback via stream-only per D-L1); correct IST and per-NVR clock offsets; bounded concurrency; hidden/abandoned streams stopped; viewing audited.
4. **Monitoring basics:** camera/NVR availability with honest states (Live / Offline / Not checked / unknown because the NVR is unreachable), offline-since, recorder and location roll-ups by cluster/region on the dashboard; check-now; stale-data handling. (The full control centre, incidents and alerts are later.)
5. **Security and operations required for production:** TLS (HTTPS/WSS) for the app and gateway; strict CSP; shared rate limits; per-purpose secrets generated and rotated; least-privilege service roles (or the documented broker fallback); go2rtc locked down (loopback, no exec, registered targets only); worker lease so a restarted or duplicate worker cannot corrupt state; durable audit of grants, sign-ins and video sessions; health pages for app, worker, gateway and database; Windows service packaging with auto-start and a one-command update; tested backup and restore (including Vault key material) in a disposable environment; load test for the media path at the planned concurrency (honestly separated from metadata scale).
6. **Look:** Drishti logo and name, visible form fields, light theme on every page, desktop and phone usable, rendered checks at 1366×768, 1920×1080 and phone width.
7. **Documentation:** administrator guide (adding NVRs, regions/clusters/locations, groups, users and rights), runbooks (startup/shutdown, secrets rotation, backup/restore, update/rollback), architecture and delivery tracker updated.

## Deferred to later releases (built after Release 1 in logical order)
Release 1.1 — clip export for administrators (jobs, quotas, expiring links, delete after download) and reports with Excel; legacy-parity extras not needed for go-live (tour mode, timeline zoom/edge-dwell, 16x, multi-camera synchronised playback, H.265 transcode option); control centre, incidents, alerts (e-mail/Teams/webhook), recording health, SD-WAN/SNMP checks.
Release 2 — endpoint agent: inventory and health, enrolment, remote screen (view/control) with the gateway enforcing view-only.
Release 3 — fleet changes (software, scripts, patching, wallpaper/screensaver, local admin passwords), Wi-Fi AP monitoring and configuration rollouts, guarded Windows deployment (lab-validated only).

## Release 1 work-package sequence
P2-3 fix round (in progress) → P2-5a/b/c locations, regions, clusters, NVRs, mappings, assets, import, admin screens, new scopes (impact map in progress) → P2-4 session registry (≤ 60 s) → T-1 "Location" wording → P2-6 hardening (service roles, outbound target restriction, shared limits, secrets) → P2-7 worker lease → P3 (global shell and visuals, multi-factor, CSP, TLS) → P4-L1 live wall and group navigation (region/cluster/location/NVR/groups, dynamic groups) → P4-L2-min playback essentials (calendar, timeline, offsets, midnight tests, stream-only fast playback) → monitoring roll-ups by region/cluster → P5.4 operational readiness (TLS, Windows services, backup/restore, health, audit) → load test + browser journeys + independent security review → Release 1 handover and **owner decision to push to main**.

## Exit criteria for Release 1 (all with evidence in the tracker)
- Cross-user/location/cluster/region/camera/action permission tests pass, including playback/export denial despite live, camera-only users seeing no IT data, multi-NVR locations, and revocation ≤ 60 s for open and previously issued tokens.
- A pilot-style rehearsal on lab fakes: add NVRs, build the hierarchy, import locations/cameras, create groups, assign users, sign in as each user type and see exactly the right cameras.
- Typecheck, lint, unit, integration, production build clean; browser journeys of the above; load test results published with workload and limits; backup/restore evidence; independent security review with no open Critical/Important findings.
- Honest limits stated: real-hardware behaviour (Hikvision firmware, H.265, real SD-WAN) is unvalidated until the supervised pilot at a real location; the pilot is the first live step in production (a small number of locations), then rollout by cluster.
